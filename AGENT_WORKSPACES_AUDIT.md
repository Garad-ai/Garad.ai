# Agent Workspaces: Phase A Audit

This audit records the existing implementation and gaps before expanding the Agent workspace into the Business and Education experiences described in the product specification. It does not claim those verticals are complete.

## Existing capabilities

| Area | What already exists | Current boundary |
| --- | --- | --- |
| Agent execution | Saved agent workflows are stored in `ext_ai_agent_workflows`; `GaradAgentToolService` selects active workflows owned by the signed-in user and executes them through `WorkflowEngine`. Runs and ordered step input/output are persisted. | Agent chat requires at least one active, runnable saved workflow and tells the model to execute one. It is not yet a general task planner that can select any authorized tool for an arbitrary task. |
| Approvals | Protected workflow steps create a persisted approval and pause the run. `AgentOperationsController` authorizes the workflow owner, rejects duplicate decisions, and resumes an approved run from its saved step. | The Agent chat previously surfaced a paused run as completed and had no inline approval action. The current change reports the waiting state and adds Agent-only approve/reject controls using the existing authorized endpoint. |
| Personal memory | `AIAgentMemory` records are private to a user, have list/create/update/delete controls, and can be injected into saved-agent `ai_call` steps. | The direct Agent chat prompt does not yet retrieve this memory. There is no workspace-scoped memory model or explicit capture/review flow for business, education, or task context. |
| Team workspaces | Existing teams support owners, active members, invitations, role assignment, seat checks, and plan/team-feature gates. Agent workspace endpoints filter teams to the owner or active member. | Teams are not yet typed as Business or Education workspaces. Agent execution, documents, artifacts, and approvals are not consistently bound to the selected team or member role. |
| Documents and retrieval | `AIChatProDocument` stores owner/chat references, extracted text, chunks, metadata, hashes, and processing status. `DocumentChatService` retrieves ranked chat-document chunks for chat context. Existing document readers support ingestion; artifact/document services support generated outputs. | Documents are associated with a user and chat, not a shared workspace/course. There is no workspace-level knowledge catalogue, version history, or verified member/teacher retrieval policy. |
| Generated artifacts | Existing services create downloadable PDF, DOCX, XLSX, and presentation artifacts, with document grounding/composition and quality-review helpers. Artifacts are associated with a user and chat. | No Business-specific approved templates/brand profile or Education-specific course/grade/rubric context is wired into Agent chat as workspace knowledge. |
| Connected applications | Providers register through a connector registry; connector records, policies, token invalidation handling, and plan-gating support already exist. Agent tools can dispatch registered connectors. | Provider availability and configuration vary by installation. The current Agent execution context does not consistently constrain tools to workspace roles or report verified connection scopes inline. Live provider operations need credential-backed testing. |
| Scheduling | `GaradScheduledTaskService` persists one-time and recurring tasks as scheduled workflows, validates time zones/cron input, and supports pause/resume. Workflow runs preserve status and step history; idempotency keys prevent duplicate runs when supplied. | Schedules are user-owned rather than workspace-owned. Business/Education report templates, destinations, quota behavior, and end-to-end delivery verification are not established for these verticals. |

## Immediate execution fix

The workflow engine already paused protected actions and resumed them after approval, but `GaradAgentToolService::run` treated `pending_approval` as success. Agent chat now reports the pending state, emits an Agent-only `waiting_for_approval` tool status with the approval ID, and renders approve/reject controls that call the existing owner-authorized decision endpoint. Chat Pro does not receive those controls or the Agent-mode status behavior.

## Follow-up: User Experience and Network audit

- Laravel route inspection confirms `/agents` and the React Chat Pro route are separate page routes. Agent social/profile APIs and connector endpoints run through authenticated web middleware; public-profile reads are explicitly unauthenticated and apply `canViewProfile`. Administrative dashboard routes are behind authentication and administrative authorization middleware. No admin dashboard routes were added to the user-facing Agents area.
- The Public Profile UI already has a real empty state for an account without a username and a link to profile settings. The profile API returns an allowlisted public payload; existing server tests cover hidden profiles, no email leakage, authenticated/idempotent follow and unfollow, mention privacy, and recipient-only collaboration decisions.
- Agent composer mentions now retain selected stable user IDs through message submission, are revalidated and persisted against the created Agent message, restore with message history, and notify only the selected eligible recipients. Mentioning does not grant conversation access. The backend enforces public-profile visibility, mention opt-in, and workspace membership where a workspace is attached; no blocking model/rule was found during implementation.
- Agent sharing now persists recipient-specific, view-only grants for one selected message part, a complete Agent conversation, or an Agent workflow run. Token values are random and only their hashes are stored; every deep-link read checks the authenticated recipient, current grant state, owner/resource relationship, workspace membership where applicable, and 30-day expiration. Owners can list and revoke grants; share notifications include the usable Agent link. Task shares intentionally expose only task name, run status/timestamps, and step type/status. No durable workflow-run-to-artifact relationship exists, so task deliverables are not shared and the UI states this explicitly.
- Connected Apps uses the existing authenticated connector controller, which filters connector records by owner and subscription plan, checks expiry/active state, and applies connector policies to view, modify, pause, and delete operations. Provider consent and OAuth callbacks remain provider-specific; live connection verification was not performed because it requires real provider credentials.
- Browser resource inspection showed the authenticated account bootstrap eventually succeeds after initial unauthenticated requests; the primary conversation/project/connector endpoints return 404 before the frontend's established legacy endpoint fallback succeeds. These are compatibility probes, not user-visible failures in the observed session. The new mention search was exercised in the Agent composer against the authenticated local app and returned the expected no-results state for a non-existent query.

## Work still required by phase

- **Phase B — Foundations:** Bind execution to an explicitly selected workspace; enforce membership roles and workspace ownership for knowledge, artifacts, connectors, task history, and approvals. Add deliberate, user-controlled memory retrieval to Agent chat with clear personal-vs-workspace scope. Verify private storage and access for uploaded/generated files before using them as shared knowledge.
- **Phase C — Business slice:** Create or select a Business workspace, ingest a reference document into that workspace, retrieve grounded facts with source attribution, generate and persist one real document artifact, and return its download link in Agent chat. Do not invent missing figures or policy facts.
- **Phase D — Education slice:** Add an Education workspace/course boundary, retrieve authorized course materials, then demonstrate an explanation, practice quiz, and feedback grounded in those materials. Do not imply access to grades or student records that were not supplied or connected.
- **Phase E — Scheduling:** Attach schedules and run history to the correct workspace, enforce role/plan limits, and verify destinations and actual delivery before reporting success.
- **Phase F — Expansion:** Add workspace templates, broader connected-app actions, reporting, and contextual UI only after the shared authorization and knowledge boundaries are in place.
- Profile and follow flows remain implemented with focused backend coverage. Browser verification and the named regression suites/build are tracked in the current continuation below.

## Current continuation: Profile, structured mentions, and secure sharing

- Profile boolean preferences are normalized for multipart requests, and username uniqueness is checked case-insensitively. Public profile/follow behavior remains in place.
- Structured mention records are message-scoped and support multiple distinct recipients while suppressing duplicate IDs. A private conversation is never exposed by a mention notification.
- Share grants are resource- and recipient-scoped. Selected-message shares return only the selected part, conversation shares return the explicitly granted conversation, and task shares omit tool inputs and raw step outputs. Invalid, unauthorized, revoked, or expired links fail without returning resource content. New shares expire after 30 days.
- The additive migration `2026_10_19_000001_create_agent_collaboration_tables.php` was applied after confirming the configured target is the local MySQL database, the three new tables did not already exist, and the migration was pending. It only creates collaboration tables; no existing conversation/profile/task records were changed or deleted.
- Task deliverables remain unsupported because workflow runs have no durable relationship to generated artifacts. Sharing a task currently grants access only to its status and sanitized step states; this is a known incomplete part of the requested task-sharing scope.
- Verification: the requested four Laravel suites passed together (37 tests, 221 assertions; one PHPUnit deprecation notice). `npx tsc --noEmit` and `npm run build` passed; Vite reported its existing large-chunk advisory. Browser verification opened the authenticated Agent route and Public Profile, and exercised a synthetic @mention lookup through the composer; the lookup correctly returned no matching users. The existing page reported that its AI provider was unavailable, so no message was sent and provider-dependent end-to-end sharing interactions could not be exercised safely in that session. The recipient authorization, notifications, expiration, and revocation paths were tested through Laravel feature tests against SQLite fixtures; these tests are distinct from provider-backed generation.

## Current continuation: Persistent Agent task activity

- The existing `WorkflowEngine` remains the only Agent execution engine. Its persisted `AIAgentWorkflowRun` and uniquely indexed `AIAgentWorkflowRunStep` rows are the progress source of truth; the engine records actual step starts, approvals, completion, and failures. Agent chat runs also record the originating chat/message IDs and use an idempotency key derived from that workflow and message, preventing a replayed tool call from repeating consequential operations.
- Authenticated `GET /dashboard/user/ai-agent/operations/chats/{chatId}/activity` returns only chat-bound runs owned by the signed-in user, with safe labels/statuses/timestamps and approval IDs. It deliberately omits raw step input/output and raw exception details. No new progress/event table or migration was needed.
- Agent Chat polls the activity endpoint sequentially (no overlapping requests), more frequently while an assistant response is streaming and with bounded backoff after transient errors. It associates runs with the assistant response by durable message ID; reopening a conversation fetches the persisted state again. Ordinary Chat Pro does not poll or render this panel.
- Approvals continue through the existing owner-authorized decision endpoint. Owners may cancel a pending approval immediately or request cancellation during execution; the engine marks the run cancelled after the current action returns and does not start subsequent steps. An in-flight external action cannot be forcibly interrupted, so the UI reports cancellation waiting for the current action.
- Browser verification used an authenticated Agent page. A safe read-only request invoked the existing saved research workflow; its run/step appeared in the panel while running and later showed completed. The stream then separately returned a provider 502 while preparing the final chat response, which remained visibly failed rather than being reported as a successful answer. A temporary two-step persisted fixture verified live step transition, terminal status update, and restoration after navigating away and reloading the conversation; temporary fixture rows are removed after verification. The real provider-backed run was single-step, not a successful multi-step provider task.
- The workflow-run schema has no durable workflow-run-to-artifact relation. The activity panel therefore does not invent file deliverables or links; artifact links remain available only through existing verified artifact flows. Safe automatic task retry is not added because repeating a completed or partially completed external workflow could duplicate side effects; same-message replays reuse the idempotent run.
- Focused validation for this continuation includes the Agent approval/state, collaboration, profile, and Chat Pro suites plus TypeScript and the Vite production build. Exact test/build results are in the completion report.

## Follow-up verification: terminal refresh and provider 502

- Agent activity polling now keys off assistant message IDs and status transitions, so stream completion, failure, or cancellation causes an immediate activity refresh even when the assistant was already outside the generating state. If a poll is already in flight, one latest refresh is queued and runs as soon as it settles; the previous 250 ms retry loop is removed. Returned runs are deduplicated by durable run ID. Active workflow runs continue to poll at the faster interval.
- The historical `claude-opus-5` 502 log entry reports `Call to undefined method Symfony\Component\HttpFoundation\ParameterBag::pull()` from local `StreamService.php` code. The logged `502` is the stream's fallback status for that PHP fatal; the log contains no upstream Anthropic response status/body for that failure. Current Anthropic configuration is present, the service targets `/v1/messages` with the supported `anthropic-version` header and 15-second connect / 300-second request timeouts, and an authenticated Claude Opus 5 tool call subsequently reached the application successfully. Its resulting 500 was a workflow validation error, not a provider error.
- Authenticated browser verification completed real run `68620` in chat `13763` / message `5703` using saved read-only workflow `35` and Claude Opus 5. Its persisted `ai_call` step appeared as running, then the run and step showed completed; the chat response succeeded. Reloading the conversation restored the completed panel. This is a real provider-backed single-step run, not a multi-step result.
- No eligible multi-step, no-external-effect saved agent was available for a provider-backed run: saved multi-step agent `18` has incomplete path configurations, `22` references unavailable context variables, and the remaining valid multi-step agents in the authenticated catalog send or reply through Gmail. Those external-effect agents were not executed. Multi-step provider-backed verification remains blocked until a safe runnable agent is available. No existing workflow, approval, connector, or user data was modified to work around that limitation; the test conversations created during browser checks remain in chat history.
- A browser activity request took about 5.6 seconds once and timed out transiently during a separate tool call; the client retries and now queues the immediate post-stream reconciliation behind any in-flight request. No database migration was added or applied.

## Agent and Chat Pro history separation

- Agent-mode chats are identified by the existing owner-scoped `ext_ai_chat_pro_agent_conversations` marker; no data migration or conversation rewrite is needed.
- The legacy conversation-history endpoint now returns the authoritative `mode` on both list and single-conversation responses and optionally filters history by `mode`. The React client maps that backend mode instead of treating every legacy chat as ordinary Chat Pro.
- Agent and Chat Pro routes request their own paginated/search history. The UI already filters each sidebar by mode, so Agent tasks remain under Agent Recent Tasks and ordinary Chat Pro recents exclude those Agent conversations.
- Browser verification switched between `/public/chat` and `/public/agents`: Chat Pro Recents did not show the saved Agent 35 task, while Agent Recent Tasks showed it and other marker-backed Agent conversations. Existing Chat Pro conversations remained in its own Recents list.

## Claude-style Agent progress and deliverables

- The Agent activity summary now foregrounds the current persisted workflow step, elapsed time, and real run status; detailed steps stay expandable, except approval requests remain expanded so their controls are visible. The duplicate generic progress card is hidden while a persisted run is actively running or waiting for approval.
- When a newly created Agent response artifact is confirmed ready and has a verified application URL, the existing authenticated artifact preview panel opens automatically. Older artifacts are not auto-opened on page load, and existing artifact cards/actions remain available.
- This is a UI enhancement over existing workflow execution and artifact storage. It does not add autonomous Gmail access, send or modify messages, or claim support for new artifact types.
- The browser restored a persisted completed Agent 35 run and showed its updated compact activity summary. Chat Pro Recents were also checked and remained free of that Agent task. TypeScript and production build passed. No new provider-backed artifact was generated solely for this UI check, so automatic preview opening for a newly generated artifact was build-verified but not observed live in this run.
